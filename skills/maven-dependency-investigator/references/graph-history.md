# Historical dependency graphs

Compare recorded dependency trees inside one investigation, using available local Git commit ancestry to establish their order. This feature does not rebuild historical revisions, fetch missing objects, check out old files, or prove what was shipped. Imported provenance remains caller-attested; Git verifies relationships between local commit objects, not whether those commits actually generated the imported reports.

## Prepare the investigation

Start with `discover` and record a candidate selection with `select`, as described in [cli.md](cli.md). The selection determines the historical subjects: each known selected group/artifact, module and realm is compared separately. The historical comparison deliberately drops the selected version, so selecting `org.example:lib-c:1.0` can still reveal changes to other versions of that same group/artifact. It does not broaden to unselected artifacts or child modules. Keep the returned `run_dir` and use the latest returned `revision` for each command that writes evidence. Candidate IDs and evidence IDs belong to that run only.

A dependency found only in a packaged archive can be selected even when its name is absent from every application POM. If its group/artifact and module are known but its realm is `unknown`, comparison is permitted only as **candidate graph history** when same-run imports explicitly attest a known realm and that exact module and contain the selected group/artifact as a non-root dependency node. The imported realm is not inferred from the selection or from a package filename.

Without those attestations, the unknown selected scope stays partial and produces no graph events. With them, the packaged subject remains unchanged with realm `unknown`; the stage remains partial and new `candidate-history-scope` qualifications apply to derived graph evidence and any dependent declaration leads. This does not prove the packaged component's realm, binary identity or historical build. No POM declaration is invented for an archive-only subject.

Obtain at least two already-recorded trees and their provenance. Each usable pair needs:

- The pinned `maven-dependency-plugin` 3.11.0 JSON tree format.
- Explicit nonverbose attestation. The default import is diagnostic verbose; diagnostic or unknown-mode snapshots remain gaps, not empty graphs.
- An explicitly attested realm, normally `project` for application dependencies. Omitting `--realm` leaves it `unknown`, which cannot establish a comparable graph group. Plugin and project realms remain separate.
- A known module identifier in provenance, such as `.` for the checkout root or `service` for that module. Known different modules are not pooled.
- Distinct full lowercase commit IDs in provenance that are available as local commit objects. Use the repository's storage format: 40 hexadecimal characters for SHA-1 or 64 for SHA-256. Branch names, tags, abbreviations, revision expressions and uppercase spellings are rejected rather than resolved implicitly.

## Import two snapshots, then collect

The following commands are a template, not captured output. Replace every placeholder with the actual path, ID or revision from your investigation. `INV` means `python3 /path/to/skill/scripts/investigate.py`.

```text
INV import --run-dir RUN_DIR --expect-revision LATEST_REVISION \
  --kind tree-json --report BEFORE_TREE --provenance BEFORE_PROVENANCE \
  --tree-mode nonverbose --realm project

INV import --run-dir RUN_DIR --expect-revision REVISION_FROM_FIRST_IMPORT \
  --kind tree-json --report AFTER_TREE --provenance AFTER_PROVENANCE \
  --tree-mode nonverbose --realm project

INV collect --run-dir RUN_DIR --expect-revision REVISION_FROM_SECOND_IMPORT \
  --graph-history

INV report --run-dir RUN_DIR --validate
```

Use `--tree-mode nonverbose` only when it truthfully describes the recorded tree. A flag contradicting a recognized provenance `format` of `verbose` is rejected. Do not relabel a verbose report to obtain inclusion evidence: that format may contain omitted dependencies without omission flags.

`--graph-history` is an explicit opt-in. Ordinary `collect` still runs its existing local history and optional usage stages; it does not add graph comparison unless this flag is present. Graph-history collection keeps those stages and publishes one expected-revision report update. A stale revision fails before collection instead of silently retrying.

The collect response includes `graph_history_outcome` and the `graph-history` stage in `stages`. Read the stored report for the evidence rather than interpreting exit code zero as complete historical coverage.

## Minimal synthetic tree and provenance

This example demonstrates the accepted structure only. It was not generated by Maven and is not historical evidence. The tree records a transitive path from `app` through `lib-b` to `lib-c`:

```json
{
  "groupId": "org.example",
  "artifactId": "app",
  "version": "1.0",
  "type": "jar",
  "scope": "compile",
  "classifier": "",
  "optional": "false",
  "children": [
    {
      "groupId": "org.example",
      "artifactId": "lib-b",
      "version": "2.0",
      "type": "jar",
      "scope": "compile",
      "classifier": "",
      "optional": "false",
      "children": [
        {
          "groupId": "org.example",
          "artifactId": "lib-c",
          "version": "1.0",
          "type": "jar",
          "scope": "compile",
          "classifier": "",
          "optional": "false",
          "children": []
        }
      ]
    }
  ]
}
```

Its synthetic provenance file can use this complete field set:

```json
{
  "producer": "maven-dependency-plugin",
  "version": "3.11.0",
  "format": "nonverbose",
  "generated_at": null,
  "revision": null,
  "module": ".",
  "profiles": null,
  "jdk": null,
  "maven": "synthetic example: no Maven execution",
  "settings_digest": null,
  "dirty": null,
  "working_tree_digest": null
}
```

The producer/version values identify the grammar illustrated here, not an observed generating process. In a real provenance file, attest them only when known; omitted or explicit `null` producer/version values retain an assumed-parser-grammar qualification. Unknown build-context fields stay `null`, never guessed.

This example parses, but `revision: null` intentionally prevents an ancestry proof. For a real pair, record each report's actual generation commit and available context in its own provenance file. Merely inserting an existing commit hash into a synthetic report does not authenticate its history. The realm is passed separately through `--realm`; it is not a provenance-file key.

## Read the result conservatively

The report adds `git-ancestry` evidence and `graph-history` evidence. The graph evidence payload contains `comparison`, source snapshot evidence IDs, ancestry evidence IDs, source qualifications and limitations. Events may be `graph-addition`, `graph-removal`, `graph-version-change` or `graph-reintroduction`; each cites its bounding snapshots and describes an inference between observations, not the exact original introduction date.

- Only a uniquely ordered sequence of compatible supplied snapshots is compared. Unrelated branches, duplicate revisions and ambiguous ordering do not become a fabricated timeline.
- Missing commit objects, unknown revisions, shallow history and legacy grafts produce explicit issues or unavailable ancestry. Nothing is fetched. Replacement refs and commit-graph acceleration are disabled for these ancestry probes.
- Local commit-object existence does not prove reachability from a particular branch or tag. The recorded proof concerns the available local graph.
- No snapshot, one usable snapshot, diagnostic trees, unknown realm/module, and incomplete semantic fields can leave coverage partial. They are not evidence of historical absence. An unknown-context snapshot that could belong to a compared group remains in its ordering as a barrier; it is not dropped so that its neighbors can be compared. Adjacent comparisons touching an unusable snapshot are skipped and prior reintroduction state is reset. Later observations therefore cannot establish a reintroduction across that gap.
- Context differences, unknown provenance and source qualifications accompany derived events. Fresh qualification records apply to derived graph evidence and dependent declaration leads, so citing only a derived record does not discard a source warning.
- Repeating collection appends fresh evidence and qualifications and updates the named stage in the new revision. Earlier immutable revisions and observations remain available.

When selected subjects have recorded declaration POM paths, collection also adds `declaration-history-candidates` evidence. Each selected project scope inspects only recorded paths whose module directory matches it exactly; selecting a root module does not implicitly select child-module POMs. Non-project or unavailable declaration scopes remain qualified. The collector may report changes to introducing dependencies as candidate leads. It does not prove that a particular declaration change caused a transitive introduction, or match that introduction to an exact event time. For an archive-only selection without declaration paths, no declaration path is invented; imported-tree comparison can still run.

The CLI uses local ancestry ordering only. The underlying comparator also supports an explicitly requested timestamp-only mode, but `collect --graph-history` exposes no such switch and never falls back to timestamp or filename order. That comparator mode accepts ASCII `YYYY-MM-DDTHH:MM:SS[.fraction]Z` or signed `HH:MM` offsets, with one through six fractional digits, offset hours at most 23 and minutes at most 59. Invalid dates, unsupported precision, invalid offsets, missing timestamps and tied instants leave ordering unresolved; excess precision is not silently truncated. Even valid timestamp ordering is temporal evidence, not proof of causal ancestry.

## Limits and permissions

Graph comparison defaults to at most 128 snapshots, 10,000 nodes per snapshot, 16 MiB of serialized comparator input, 24 MiB of output and 20,000 events. Individual report imports are bounded separately. Limits yield rejection or qualified coverage, never silently truncated authoritative history.

The ancestry collector has its own aggregate 10-second deadline and 1 MiB output budget. Each selected-scope declaration collector separately receives a 10-second limit, 1 MiB output cap and a 64-commit bound. Ordinary history and usage collection also retain their own limits. These are not one combined hard wall-time limit for `collect`; parent filesystem operations and process creation are not hard-interruptible.

The local Git probes require default SIGCHLD handling and exclusive child reaping. Unsupported handlers are refused; concurrent external reaping and transient change-and-restore of that policy are not atomically prevented. Repository observations are not an atomic snapshot against concurrent same-user changes.

No Maven or external lookup approval is needed for this local comparison because it performs neither. Obtaining fresh trees by executing Maven, or retrieving missing reports from a remote service, remains a separate permissioned operation. See [permissions.md](permissions.md) and [interpretation.md](interpretation.md). Missing evidence never justifies executing a historical build or fetching data automatically.
